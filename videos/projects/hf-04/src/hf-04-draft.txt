哈喽大家好，我是叶扬。

先把上一集的成果打开看一眼：第二秒，标题「我的第一个片段」出来了。可你盯着看——它不是「进来」的，是「砰」的一下，杵在那儿的。静态页面嘛，只会出现和消失，不会动。

今天这集，就让它飞进来。

这是整个系列最核心的一集。我先把话说在前头：在 HyperFrames 里写动画，跟在普通网页里写动画，规矩不一样。不一样在哪？不在语法，在这东西的播放方式。

按老习惯，让一个块飞入，CSS 写个 keyframes 就够了：起手透明、往下挪六十像素，零点八秒，归位。保存，回到浏览器点播放——哎，标题确实飞进来了，挺正常。

可别急着下结论。你得先知道，渲染器出一条三十帧每秒的视频，到底是怎么干活的。

它不是从头把网页播一遍、在旁边架个摄像机录。它干的事是：要第几帧，就算出这一帧的秒数 t，然后问页面——把你拨到 t，你长什么样？摆好，截图，下一帧。注意，它要帧的顺序是随机的：这一秒还在问你第二秒，下一秒可能直接问你第七秒，不会从头等你七秒。

所以页面上每一样会动的东西，都得回答同一个问题：给你任意一个秒数，你能不能立刻摆出那个瞬间的样子？不用等，也不依赖之前发生过什么。这个特性，英文叫 seekable，可定位。是这类工具的命根子，也是它敢说自己为 agent 而生的底气——同一份输入，第几帧是什么，板上钉钉。

那刚才那段 CSS 动画，到底能不能被定位？我不猜，截帧看。用 snapshot，分别截第二点一秒、二点五秒、二点九秒三张。

结果有点出乎意料：三张全对。二点一，淡淡的影子刚冒头；二点五，半透明，停在半路；二点九，白了，归位了。我不放心，同样三个时刻，再截一遍——两张图逐字节一模一样，一个像素都不带差的。

原来 HyperFrames 的运行时，偷偷替你做了一件事：它把 CSS 动画的时钟接管了。你写的动画不再是页面一加载就自顾自播，而是被绑到了片段自己的时间轴上——标题第二秒进场，动画就在第二秒开始。运行时替你拨，所以帧帧都对。

听到这儿你可能想：那还学什么，CSS 全搞定了？

别急，我们再试一样东西。我在页面上加个计数器，用最普通的 setInterval，每半秒把数字加一。浏览器里看，数字跳得欢着呢，一点毛病没有。

还是不猜。先排队来：同一个第二秒，我连截三张，三张全是 tick 三，逐字节一模一样。你可能觉得，定时器这不挺老实吗？那是因为它们排着队，机器也闲。正式出片可不是这么出的。我写了个小脚本，喊六个渲染器同时开工，全问第二秒，谁也不许等谁。六张图回来——好几个不同的数【彩排参考：tick 四、tick 六、tick 七；正式 take 后按终端分组回填】。同一个第二秒，六回好几个样。因为 render 默认就是多个无头 Chrome 并行、帧还乱序要，大家挤一块抢 CPU，跟我这脚本，一个场面。

为什么 CSS 动画行，定时器不行？因为 setInterval 只认墙上的钟：页面打开后真实过了几秒，它就跳几下。渲染器问它「第二秒你长什么样」，它答不上来——它只会告诉你「我现在是什么样」；而这个「现在」，取决于它那个进程这会儿抢不抢得到 CPU——被挤狠了，等终于轮到它截图，计数器已经多跳了两三下。你看，连 check 都是绿的，零错误。守门员能查布局、查对比度，但查不出你这个动画根本没法定位。这一课，只能自己懂。

所以规矩是：凡是跟着真实时间自己往前跑的东西——setInterval、setTimeout、requestAnimationFrame 里手改样式——在视频里都是薛定谔的画面。动画的时间，必须交给一根能来回拨的轴。

官方给的正道，是 GSAP 的时间轴。页面骨架底部其实早就替你把位置留好了，今天把它讲明白，三件事。

第一件，建时间轴的时候加参数 paused 等于 true。这条轴生下来就是暂停的，一秒钟都不自己走。它不是一段会播放的动画，它更像一个函数：你喂它一个时间 t，它还你那个瞬间每个元素该有的样子。

第二件，动画照写，但是往这条暂停的轴上挂。我写 fromTo：标题开头透明、往下偏六十像素，零点八秒浮上来，缓动用 power2 点 out；最后一个参数写二——这是挂在时间轴上的位置，标题第二秒进场，动画就从第二秒起。卡片挂第三秒，副标题挂第六秒，各就各位。暂停着没关系，它全记得住。

第三件，最容易忘：window 点 __timelines，中括号 main，等于这条轴。main 是谁？回头看 #root 身上那个 data-composition-id，就是 main。这行是报到：渲染器渲染 main 的时候，按名字来这张表取轴。底下还留一行 tl.seek(0)，页面一摆好先定位到第零秒，省得开头闪一下终态。

有人可能发现了：我刚才偷懒，不注册、直接写全局 GSAP 动画，运行时好像也能兜住，截帧也对。没错，眼下这个版本，运行时确实会好心帮你代理简单的全局动画。但记住，那是它「猜中了」，不是「保证了」：一条轴上几十个动画、有相对位置、有嵌套、有瞬间跳变，代理猜不过来。显式注册，才是写进合同里的规矩。写能被保证的代码，别写指望别人聪明的代码。

三行凑齐：暂停的轴、挂在轴上的动画、注册到表里。回浏览器，播放——第二秒标题干干净净浮上来，第三秒卡片弹一下，第六秒副标题进场。

光这样还不过瘾，我打开开发者工具，在控制台亲手拨给你看。

页面上有个现成的播放器对象，window 点 __player，它身上就有 seek 方法。喂二点四——画面「啪」地回到半透明、浮在半路的样子；seek 三，标题就位；seek 六点三，副标题在半路；seek 九，全在；seek 零，空舞台。我连着五回 seek 同一个二点四，五回画面一模一样。时间在这儿是能倒着拨、来回拨的，拨到哪儿是哪儿。

有人可能想，刚注册到 window 点 __timelines 上的那条轴，我直接调它的 seek 不就行了？还真不行。轴管的是动画值，可一个片段第几秒露面、第几秒退场，是播放器管的。你直接拨轴，数值拨回去了，人还藏着——第九秒标题的透明度是一，画面上却没有它。所以亲手拨，找 __player：它一声令下，轴和片段一起就位。

顺手送你一条踩过的坑：交给时间轴的动画，只让它一个人管。位移、缩放、透明度，都在 transform 和 opacity 上，没问题；但你别手贱，再给同一个元素写一条 CSS transition——两个管家抢一个属性，渲染器瞬间设值、过渡想从头补间，同一秒截两回，可能就是两张脸。一个属性，一个管家。

到这儿，可以把渲染那层的窗户纸捅破了。

render 出片的时候，无头 Chrome 干的事，跟你刚才在控制台里干的一模一样：帧号除以帧率算出 t，调一声 seek，时间轴把所有元素瞬间摆到位，浏览器把这一帧的样式算完，截图。一帧一帧 seek、一帧一帧截，最后交给 FFmpeg 烤成 MP4。你刚才在控制台里手拨，等于人肉当了一回渲染器。

也正因为如此，GSAP 不是唯一选择。它只是样板里替你接好的一种。CSS 动画、浏览器原生的 WAAPI，运行时能自动接管；Lottie、Three.js、Anime.js，乃至你自己写一个对象，里面实现一个 seek(t) 方法，都能挂到这张表上。渲染器不在乎你轴里存的是什么，它只认一个约定：我喊 seek(t)，你得让画面立刻就位。适配器模式，老程序员一看就懂。

这集的行动件也清楚了，回去看你自己的 index.html，查三条：动画的时间是不是交给了一根能来回拨的轴，而不是跟着墙钟自己跑；GSAP 时间轴是不是 paused 等于 true，动画都带时刻挂在轴上；有没有注册到 window.__timelines、名字跟 data-composition-id 对得上。三条齐，你的动画才是能被渲染的动画。

今天从一段「看着没问题」的计数器，讲到了整类工具最底层的约定：不是让画面动起来，而是让任意一秒的画面，随叫随到。

灵魂在 seek。
