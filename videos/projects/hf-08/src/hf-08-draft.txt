先做一个实验。

同一份工程，十三秒，黑底上五道白闪，干净得不能再干净。我用 render 把它烤成 MP4，烤完一遍，再烤一遍，两份文件摆一块儿算指纹——一模一样，一个字节都不差。再把六天前烤的旧档翻出来比，还是同一个指纹。我又换了三种烤法：软件 GPU、软件单 worker、硬件 GPU 单 worker，连新带旧六份文件，六个指纹，同一个。

做视频的人都知道，「渲染」这两个字名声不太好：同一份工程，今天烤和明天烤，这台机器和那台机器，常常给你不一样的结果。而这里连软件 GPU 和硬件 GPU 两条完全不同的路，烤出来都逐字节相同。上一集照片都验干净了，这一集真烤——无头 Chrome 怎样把网页烤成 MP4，上万帧要烤多久，烤崩了又怎么查。

先说清楚一件事：render 不是在「播放页面，顺手录屏」。录屏是墙钟的生意，播放一遍就得老老实实花十三秒，机器卡一下、后台忙一下，录进来的全是现场实况。render 不认这个。它把时间轴当成一道数学题：每秒三十格，十三秒，三百九十格，每一格都是一次独立求解——把时间轴 seek 到这个时刻，等浏览器把画面彻底画稳，再截一张图。第一格、第一百格、第三百九十格，谁先求谁后求无所谓，求多少次，答案都得一样。三百九十张静态图到手，交给编码器压成视频流；声音走另一条路，单独处理、按时长归一，最后两路合成一个 MP4。

上一集说过，视频最怕的不是丑，是不确定。这套「逐格求解」就是确定性的根：每一帧的画面只由时间码决定，墙钟被彻底关在烤炉外面。也正因为如此，同一份工程才敢烤六次，六个指纹完全相同。

烤一次到底经过几道手？render 有个 --debug 开关，打开之后中间产物一件不扔，我把整个目录摊开看过。先是编译，把工程连同动画运行时打包成一个自足的页面，附一份媒体清单；然后开一个无头 Chrome 探路，看这台机器的硬件 GPU 能不能用；接着在三百九十帧里挑五帧真截一遍，量一量在这台机器上截一帧要多久，给后面派活提供依据；再往后，每个 worker 领走一段帧号，各开一个无头 Chrome，逐帧 seek、截图，图片落盘；最后是编码与合成：三百九十张图先压成无声视频，再跟声音合到一起。

工程里要是还嵌了视频素材，烤之前会多一道抽帧，把素材也变成一张张图，而且按内容做缓存——同一份素材抽过一次，下回直接用，不重复劳动。有个参数能把这份缓存挪出系统盘，盘紧张的用得上。还有更彻底的一步：不想要 MP4、只要图，有一种格式直接输出三百九十张 PNG 加一条声音，三点二兆，一眼看见烤炉的原始产品。

那三百九十张图是怎么截出来的？有两条路。

第一条是截图法，软件 GPU 上场。无头 Chrome 用 CPU 模拟一块显卡，名字叫 SwiftShader，每个时刻用浏览器自带的截图命令把画面截下来。这条路可以多个 worker 并行：三个无头 Chrome 同时开工，各领一段帧号，图先全部存到盘上，等三家都交活再统一编码——并行截图的时候没法边截边编，这是门控决定的，不是我安排的。第二条是硬件路：先探一次硬件 GPU，我这台机器上的集显探活成功，于是换一套捕获方式，不让浏览器「截图」，而是让 Chrome 的合成器直接把画面交出来。这条路在我这台机器上恒为一个 worker，好处是边抓边编码，抓完也编完了。

时间账也报一下。十三秒的小工程，软件路首跑六十八秒，其中光开浏览器、量帧就花掉十六秒；第二回浏览器热了，五十六秒以内。硬件路五十四秒，编码和抓帧重叠在一起。小工程谁也快不到哪去，启动成本摊不开。长片才见真章：我上一个片子，一万六千七百七十七帧，硬件路单 worker，抓帧本体三十九分钟，全程四十一分四十三秒，折下来每秒七帧左右。知道这个数，开烤之前心里就有钟。

worker 的数量不是拍脑袋的，是算出来的，我去源码里把账翻出来了。它同时算四笔：CPU 核数减二；总内存的一半除以每个 worker 一千五百三十六兆的预算；总帧数除以三十；再给内存堆留一笔账。四笔取最小，大工程还要再被一道系数压一压。拿我这台八核、十六 G 内存的机器算：CPU 给六个，内存给五个，帧数给十三个，最后被压到三个——和烤的时候日志里报的数一模一样。帧太少也不并行，不到六十帧，直接一个 worker。

那硬件路为什么偏偏钉死一个？这里有三层。短工程帧少，并行连启动成本都赚不回来；长片呢，代码里写得很直白，超过九百帧之后，单 worker 边抓边编在实测里全面更快，于是它主动把多 worker 反转成一个。你可能要问：硬件这么快，为什么不能开三个 Chrome 一起抓？这个功能真有，三个并发，门槛是二十四 G 内存。为什么卡这么高？代码注释里留着事故档案：老版本在十六 G 的机器上开过三个，烤出来的片子出现了竖直黑条——三个硬件实例抢内存，合成器的画面瓷砖被挤掉，而抽检验证又恰好漏看了那几格。打这以后，地板以下只开单 worker。我这台十六 G，正好在线外。

开烤前「挑五帧量一量」也不是摆设：构图越贵，截一帧越慢，着色器转场、iframe 这些都会抬高成本，实测耗时会反过来调整 worker 数，防止浏览器合成器被活活饿死。

再说门控。render 开烤前会自己先跑一遍 lint，但注意，默认设置下，lint 有 error 它并不拦。我故意烤了一个坏工程：红方块用 requestAnimationFrame 自己掐着表跑，上一集说过的墙钟黑户。lint 报了两个 error，render 照样出片。我把成片拆开看帧：第一秒，红方块刚离开起点一点；第五秒，它正好走到屏幕正中——按它的匀速，十秒一个来回，第五秒恰好在半程。墙钟动画真真切切烤进了 MP4，它不跟你商量，好坏照烤。想让它拦，加 --strict，lint 不过直接中止，一片不出。所以 check 零 error 是流程纪律，是你给自己上的锁，不是 render 的强制前提。

但「默认宽容」不等于什么都放。我又试了一个工程，音频文件根本不存在。这一回它没客气：画面一路烤完，临到合成，发现声音的源头是空的，输出会变成一条哑巴片——这是正确性问题，不是整洁度警告，默认模式也直接失败退出。宽容的是「画面有嫌疑」，不宽容的是「少一条轨道」。还有个小坑：页面没注册时间轴，又忘了贴 data-no-timeline 标记，render 会死等时间轴注册，最多等四十五秒才放弃。纯静态页面记得贴标记，每烤一次省四十五秒。

真崩了怎么办？记住三样东西。--debug 留下的目录是第一现场：编译产物、每一帧的图、无声视频、音频、阶段账本全在里面，账本把每一段花了多少毫秒列得清清楚楚，先看时间死在哪一段。日志里要是出现 worker 静默退出，八成是内存问题，它自己都会建议你用 -w 降到一个 worker 隔离重烤。长片烤到一半崩了也不必从头哭：分段捕获的结果可以保留，加参数从断点续烤。浏览器开页面六十秒、协议通话三百秒、等就绪四十五秒，三道超时各有各的开关，慢机器自己放宽。画质三档、格式六种，也都在参数表里，留给发布前那一道。

到这里，八集一条线就闭环了。第二集 init 搭起骨架，第三集把网页摆上时间轴，第四集把灵魂交给 seek，第六集配上声音，第五集 check 把门，上一集用 snapshot 把每一帧看清楚，这一集 render 出炉——从一份 HTML 到一个 MP4，全程没有黑箱，每一步都能看、能验、能复算。第一集我就说，这东西最硬的承诺是确定性：同输入、同版本，同输出。今天这个六个指纹完全相同的实验，就是那张承诺的验收单。

行动件：挑一个你手上的短工程，真刀真枪 render 一回，加上 --debug，打开那个目录，看看属于你的几百张图；然后再烤一遍，自己算一次指纹，看它是不是一模一样。

第一季到此完结。HTML 能在本机烤，就能在云端烤——官方还留着 cloud、lambda、cloudrun 一路命令，把烤炉搬进机房，多台机器一起烤，还有 benchmark 帮你选档。第二季，我们离开本机，去云里烤片。

我是叶扬，我们下期见。
